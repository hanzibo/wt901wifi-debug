# ARM / Jetson 双臂遥操作优化记录与后续路线

更新日期：2026-10-25。

本文记录已经实施的优化、验证证据、未实施方案和迁移参考。
性能数据截至本日期；已实施方案随本仓库提交，原始录制和个人配置不随 Git 发布。
具体实验记录见 [VALIDATION.md](VALIDATION.md)，运行方式见 [README.md](README.md)。

## 1. 适用范围与结论

目标设备为研华 MIC-711D-ON3A1 / Jetson Orin Nano 8GB：

- Ubuntu 20.04.6 / aarch64 / L4T 35.4.1。
- 保留系统 Python 3.8；项目 `.venv` 使用 CPython 3.11.17。
- NumPy 1.26.4、SciPy 1.13.1、Numba 0.61.2、llvmlite 0.44.0。
- PySide6-Essentials 6.7.3、Ruckig 0.19.4。

当前路径：六台约 50 Hz IMU，经局域网 UDP 接收，逐包姿态积分与重力纠倾斜，
手动轴映射，双臂六关节及手掌目标 IK，再限速/限加速度输出真机指令。
没有 RGB-D 航向修正、穿戴标定、手指控制或关节位置反馈。
预览显示人体估计姿态及指令 FK，不是真机测量。

**主要收益来自两方面：Numba 缩短计算；独立进程减少完整负载下的运行竞争。**
后台采集、直接交付和最新快照语义则保障结果能及时用于控制。
当前未使用 GPU/CUDA。未通过降低精度、放宽超时或取消保护获得性能。

## 2. 如何理解指标

| 指标 | 含义 | 注意事项 |
| --- | --- | --- |
| 中位数 / P50 | 一半样本耗时不超过该值 | 不代表慢帧表现 |
| P95 | 95% 样本耗时不超过该值 | 仍有约 5% 更慢，不是最大值 |
| P99 / 最大值 | 尾部耗时 / 本次观测最慢值 | 必须同时观察，短录制无法覆盖所有尖峰 |
| 墙钟时间 | 从开始到结束经过的真实时间 | 包含计算、等待及调度等影响 |
| 线程 CPU 时间 | 该线程实际获得 CPU 执行的时间 | 与墙钟之差不等于纯 GIL 等待 |
| 输入年龄 | 当前时刻距离目标所依赖输入被读取的时间 | 双臂按参与计算的最旧输入；不是 IK 耗时 |

IK 完成不会刷新输入的原始有效期。读取后等待、姿态处理、IK 和输出等待都可能增大年龄。
现有输入年龄不包含 IMU 内部采样、无线在途和电机实际响应时间。
不同阶段的分位数不能直接相加为端到端分位数。

## 3. 已实施的优化

### 3.1 初始 IK 异步准备与界面减负

- 初始求解放入 `InitialIKWorker`，避免在 Qt 主线程同步计算。
- 减少界面更新积压，使控制状态不依赖界面绘制及时完成。
- 准备完成后重新检查输入新鲜度、参考、配置和授权，不因后台求解完成就直接运动。
- 当前进程版也在后台创建、预热 IK 子进程，首次编译不放入实时跟随过程。

对应：`initial_ik.py`、`window.py`；历史提交 `cae8b57`。
主要改善启动响应和界面阻塞，不等于直接降低每次 IK 的数学计算量。

### 3.2 采集、姿态处理与控制交付脱离界面

- `PoseService` 后台接收和处理 IMU，不依赖 Qt 显示定时器读取输入。
- `LiveIK` 读取完整姿态快照，校验后将结果直接交给串口控制器。
- 界面接收结果用于显示，不再作为结果进入控制链路的必经中转站。
- 参考变更、会话撤销、停止和输入有效期仍由后台与写出端检查。

对应：`backend.py`、`window.py`、原项目 `real_robot_transport.py`；历史提交 `d85c5fd`。
虚拟串口回归包含界面停顿场景；这不意味着整个系统具备硬实时保证。

### 3.3 最新完整快照，一个请求在途

- 每次求解完成后重取最新姿态，不为控制排队补算所有历史目标。
- 当前进程管道最多有一个未完成请求，不使用多任务 FIFO 或进程池堆积目标。
- 该语义在独立进程之前已经存在，进程方案保留并测试它，并非本次才首次引入。
- 原始 IMU 角速度仍逐包积分；跳过中间目标版本不等于丢弃原始积分数据。
- 已完成但过期、属于旧会话或旧参考的结果不能重新授权输出。

对应：`backend.py`、`process_ik.py`、`tests/test_backend.py`。
测试覆盖阻塞一次求解时版本 2…100 被替换，后续仅解最新版本 100。

### 3.4 Numba / LLVM 编译 CPU 几何热点

- 将 PoE 运动链、位置残差和正则项等频繁调用的计算编译为 CPU 机器码。
- 使用 `@njit(cache=True, nogil=True)`；缓存编译结果，编译区允许释放 GIL。
- 使用 float64，不使用 fastmath；保留小角 SE(3) 平移项约定。
- SciPy 分阶段优化、SO(3) 旋转对数和数值差分仍保留，不是把整个 IK 全部编译。
- 启动前预热并对照原实现；编译或数值自检失败阻止启动，不静默降级。

对应：`fast_geometry.py`、`benchmark_ik.py`、`requirements.txt`；历史提交 `46bfb8b`。

同一组 40 帧合成双臂目标、无 profiler 干扰的板端结果：

| 实现 | 中位 ms | P95 ms | 最大 ms |
| --- | ---: | ---: | ---: |
| 原 CPU 实现 | 47.56 | 51.42 | 64.50 |
| Numba CPU 几何 | 20.40 | 22.34 | 27.71 |

最大关节差约 `1.09e-7` 度。首次 JIT 约 11.4 秒，单独记录，不计入稳态耗时。
这是合成目标对照，不能与另一组真人动作耗时直接拼接成加速倍数。

### 3.5 独立 IK 进程：完整负载下的关键优化

- 使用 `multiprocessing` 的 `spawn`，为 IK 建立独立 Python 解释器。
- 子进程重建原几何、限位、人体参考和上一解，继续使用 SciPy 与 Numba 几何。
- 用两条单向 Pipe 通信；一个请求在途，不把 Qt、UDP 或串口对象传给子进程。
- 双臂目前仍在一个子进程内按右臂、左臂顺序求解，不是左右各一个进程。
- 子进程禁止打开 socket 和机器人 tty；只负责计算，没有运动授权。
- 退出、取消或异常回收子进程；异常触发暂停，不自动重启或换后端继续运动。

对应：`process_ik.py`、`backend.py`、`initial_ik.py`、`window.py`。

相同旧录制的 163 次输入、相同初值，板端正序/反序对照如下。
数值为中位 / P95 / 最大，单位 ms；排除启动预热，进程组包含通信往返。

| 负载 | 第一轮 | 反序复测 |
| --- | --- | --- |
| 线程，仅 IK | 42.61 / 54.36 / 286.09 | 42.56 / 54.24 / 73.22 |
| 线程，加姿态、离屏 GUI、日志 | 143.98 / 211.84 / 291.31 | 129.44 / 197.40 / 300.00 |
| 独立进程，仅 IK | 31.94 / 40.04 / 51.22 | 31.47 / 38.43 / 48.13 |
| 独立进程，加姿态、离屏 GUI、日志 | 33.12 / 42.14 / 56.26 | 33.24 / 41.41 / 50.75 |

各组关节输出最大差异为 0 度。固定输入对照保留全部帧，仅用于比较，不是生产排队策略。
这证明进程隔离显著减少完整负载的拖延，但不能把收益全部归因于 GIL。
CPU 调度、频率、运行库和内存竞争等影响尚未完全分离。

### 3.6 可观测性与验证工具（支持优化，不等于算法加速）

- 限时诊断录制按钮：复用接收器，不额外占用 UDP，不授予机器人输出权限。
- 有界队列、后台写盘、完整性标记；记录不完整不能当作完整证据。
- 记录 IMU 内核收包/应用读取、姿态处理、每侧 IK、CPU/墙钟、交付及界面耗时。
- `replay_ik.py` 对比原始/编译几何；`benchmark_pipeline.py` 做分组负载及线程/进程对照。
- 离线工具禁止打开 Python 网络/串口，使用文件输入和虚拟串口回归。

对应：`diagnostics.py`、`solve_timing.py`、`benchmark_pipeline.py`、`replay_ik.py`。
历史提交 `46bfb8b`、`1934af3`；当前进程对照有后续工作目录改动。
已有记录：PC 隔离环境和板端各 63 项入口测试通过，原 PC 真机相关 165 项通过。
这些测试不代替真机物理安全与长期连续运行验证。

## 4. 如何定位到同进程负载竞争

另一组相同输入的分段负载实验，中位墙钟 / 本线程 CPU 时间如下（ms）：

| 负载逐项增加 | 第一轮 | 反序复测 |
| --- | --- | --- |
| 仅 IK | 42.11 / 41.79 | 42.43 / 42.17 |
| 加录制 IMU 姿态处理 | 94.33 / 57.60 | 86.99 / 55.36 |
| 再加离屏 Qt 界面 | 101.91 / 56.90 | 105.87 / 58.04 |
| 再加诊断 JSONL | 128.94 / 60.30 | 129.87 / 60.63 |

相同输入不需要真机串口，也能复现约 129 ms 的拖延，故优先隔离 IK，而不是更换 USB。
不能把相邻组中位数之差当作某模块独立耗时；各负载也会改变调度和频率。
一次仅 IK 峰值也有显著实际 CPU 消耗，具体原因未确认，未从数据中删除。

### 5.1 各阶段诊断耗时

单位 ms；收包范围为六设备各自分位数的范围，最大值取全部设备最慢值。

| 指标 | 中位 | P95 | 最大 |

| 每设备收包间隔 | 19.98–20.07 | 27.23–28.09 | 81.56 |
| 内核接收到应用读取 | 2.01–2.82 | 8.03–9.63 | 37.35 |
| 单包读取后解析 | 0.072–0.086 | 0.103–0.115 | 0.524 |
| 单包姿态更新 | 0.832 | 1.478 | 10.089 |
| 姿态快照发布 | 2.781 | 7.521 | 20.252 |
| IK 前读取/校验 | 0.336 | 3.153 | 17.855 |
| 右臂子进程计算 | 13.275 | 17.846 | 24.771 |
| 左臂子进程计算 | 11.929 | 17.342 | 20.872 |
| 双臂子进程总计算 | 25.841 | 32.299 | 40.752 |
| 往返减子进程计算的逐帧差 | 1.930 | 6.854 | 18.241 |
| 双臂 IK 外层调用 | 28.493 | 36.136 | 46.552 |

### 5.2 全程随动的新旧对照

数值为中位 / P95，单位 ms。

| 指标 | 旧线程方案 | 新进程方案 |
| --- | ---: | ---: |
| IK 调用 | 132.49 / 174.13 | 28.47 / 36.45 |
| 新目标交付间隔 | 136.96 / 184.92 | 31.20 / 41.24 |
| 求解开始时输入年龄 | 31.83 / 51.86 | 29.57 / 45.31 |
| 交付时原输入年龄 | 166.01 / 220.31 | 59.27 / 77.71 |
| 写帧循环检查时输入年龄 | 235.26 / 339.61 | 74.46 / 101.34 |
| 串口 write | 1.42 / 6.95 | 0.51 / 3.80 |
| 串口写帧间隔 | 54.52 / 60.77 | 53.36 / 57.60 |

旧写帧统计包含 gap 和末尾暂停；新会话全部随动写帧均为 active。
旧诊断窗口 IK 中位 129.16 ms，与全程随动 132.49 ms 的样本范围不同。
两次真人动作不同，因果判断应结合第 3、4 节的同输入实验。

新会话实际目标更新约 31.29 Hz，串口实际约 18.59 Hz，而配置为 20 Hz。
当前写帧完成后再等待 50 ms，另有调度开销，所以不是精确 20.00 Hz。
不能把串口 write 返回视为控制器已执行或电机已到位。

## 6. 旧方案为什么频繁撞超时

原始输入读取后 250 ms 为新鲜度期限；过期进入 gap，最多再减速等待 250 ms。
硬期限不会因过期结果或迟到结果被刷新，锁止后不能自动恢复。

旧方案交付年龄 P95 已达 220 ms，所剩有效期约 30 ms。
但下一目标的典型间隔约 137 ms，导致反复减速与恢复。
旧会话进入自动随动后约 20.09 秒发生硬超时；该阶段有 135 次 gap、134 次恢复。
全控制会话（含接管过渡）则是 138 次 gap、137 次恢复，勿混用统计范围。

最后一次失败：第 162 次计算耗时 182.37 ms，结果超过自身期限约 5 ms，被丢弃；
第 163 次耗时 202.32 ms，完成时比上一有效目标的硬期限晚约 37 ms。
即使第 163 次自身未过期，原会话已锁止，仍不得自动恢复。
所以“500 ms”不是单次 IK 的最大允许耗时；多次更新不及时也会耗尽期限。

新方案交付年龄 P95 约 78 ms，目标间隔 P95 约 41 ms，正常有效期内已有明显余量。
本次收益是及时交付，而不是延长安全等待。

## 7. 未实施的优化：候选项，而非当前功能

以下方案只是后续研究或工程候选，尚未实现，也没有板端收益证明。

| 候选 | 可能改善 | 尚未做的原因 / 验证条件 |
| --- | --- | --- |
| 解析 Jacobian，替代数值差分 | 减少残差重复计算 | 需覆盖位置、朝向、正则及分阶段任务；做有限差分对照 |
| C++ / Eigen 等原生完整 IK | 减少 Python/SciPy 回调开销 | 工程与维护成本较高，先证明剩余热点值得重写 |
| 调整求解算法、步数或容差 | 缩短慢帧求解 | 可能改变精度、收敛性和关节连续性，不能未经验证就减少迭代并上线 |
| 左右臂分别独立进程并行 | 缩短双臂串行总耗时 | 需测 CPU 争用、同步与单侧失败；不允许混合不一致目标 |
| GPU / CUDA / cuRobo 类求解 | 更复杂或批量任务加速 | 当前单目标小型 IK 已达标；通信、框架及模型改写成本待测 |
| 共享内存替代 Pipe | 减少通信/复制开销 | 当前成本较小；需处理版本一致性、所有权与退出清理 |
| 编译更多姿态/朝向残差计算 | 减少父进程或剩余 IK 热点 | 先单独 profile，避免重写非瓶颈；不能破坏滤波语义 |
| 更少分配、缓存、降低日志序列化成本 | 缩小长尾抖动 | 有界异步写盘已存在，仍需检查剩余分配/GC/序列化热点 |
| CPU 绑核、线程数限制、功耗/频率策略 | 改善调度与降频尖峰 | 未作为本次优化设置；需评估整机温度、功耗和采集线程资源 |
| 实时优先级 / 实时内核 | 改善调度确定性 | 权限和系统风险高，不应将普通 Linux 当前表现称为硬实时 |
| 串口使用绝对周期调度 | 更接近配置的 20 Hz | 需避免延误后突发追帧，保留过期和停止检查 |
| 网络拓扑或驱动进一步调优 | 降低收包长尾 | 本次未改网络换取收益；需根据每设备内核/应用时序定位 |

“已有上一解作为初值”不属于待新增优化：当前方案已经保留原求解历史。
“后台采集、异步日志、JIT 预热、最新快照”也已存在，不应作为未来新功能重复计算收益。

### 未完成的验证与计时

- 10–30 分钟或更长热机测试，持续记录温度、频率、P99、最大年龄与 gap。
- 轨迹规划、调度和 USB/控制器处理尚未分别完整计时。
- 设备与主机时钟未同步，不能准确拆分 IMU 内部与无线单向时延。
- 真实电机响应/到位无反馈；需同步视频或控制器/编码器反馈才能量化。
- 当前有 CPU 频率快照，但未完成温度、功率、调度和所有慢帧原因的系统归因。

## 8. 不作为性能优化手段的改动

- 不放宽 250+250 ms 保护来掩盖算不及时。
- 不给旧结果补上新的时间戳，不在硬超时后自动恢复。
- 不跳过限位、速度和加速度约束，不跳跃发送目标角。
- 不忽略求解、串口或子进程异常继续运动。
- 不随意丢弃原始角速度积分包。
- 不通过取消重力纠倾斜、降低精度或改变目标任务伪造同等结果。

## 9. 迁移到其他设备的验收参考

这些是本次成功案例导出的工程目标，不是通用机械安全标准。
硬件不同、动作不同、checkpoint 不同，耗时都可能改变。

| 项目 | 建议初始目标 |
| --- | --- |
| 六台 IMU | 每台约 50 Hz，收包间隔 P95 ≤35 ms |
| 内核接收到应用读取 | P95 ≤10 ms |
| 单包姿态更新 | P95 ≤2 ms，整体不持续积压 |
| 姿态快照发布 | P95 ≤10 ms |
| 双臂 IK 外层调用（含往返） | P95 ≤40 ms，P99 ≤50 ms |
| 新目标交付间隔 | P95 ≤50 ms，P99 ≤60 ms |
| 写帧循环检查时输入年龄 | P95 ≤110 ms，P99 ≤130 ms |
| 输入年龄尖峰 | 同级短测争取 ≤180 ms，仍需长测最大值 |
| 串口写帧间隔 | P95 ≤60 ms，P99 ≤65 ms |
| 串口 write | P95 ≤5 ms |
| 连续性 | 正常链路不应反复进入 gap，也不应故障超时 |

优先沿用当前成功的 CPU JIT + 进程隔离路径，不先引入 GPU 或更换求解器。
如不达标，先区分输入慢、计算慢、进程调度慢和写出慢，再针对一项做 A/B 验证。

## 10. 复测步骤与命令

先保存程序提交/工作目录差异、依赖版本、checkpoint、设备映射及录制文件。
排除首次 JIT / 创建进程的预热耗时，但单独记录启动耗时。
以下命令均在仓库根目录执行，路径占位符须替换为同一次录制。

```bash
# 合成目标：原几何与 CPU JIT 对照；profile 为独立采样。
.venv/bin/python -m jetson_teleop.benchmark_ik --frames 40 --profile

# 文件回放：不接网络和真机串口。
.venv/bin/python -m jetson_teleop.replay_ik \
  recordings/jetson_ik/<录制目录>/diagnostic.jsonl --max-frames 300

# 同输入、正反顺序：线程/进程及纯 IK/完整负载对照。
QT_QPA_PLATFORM=offscreen .venv/bin/python -m jetson_teleop.benchmark_pipeline \
  recordings/jetson_ik/<录制目录>/diagnostic.jsonl \
  --control OptUSBProj-ubuntu/recordings/real_robot_imu/<对应控制目录>/control.jsonl \
  --stages ik logging --backends thread process --repeats 2

# 回归测试；不要与正在占用相同输入资源的实测混为一谈。
QT_QPA_PLATFORM=offscreen .venv/bin/python -m unittest discover -s jetson_teleop/tests
```

离线回放的滤波历史和离屏界面不等于完整真人运行环境。
先验证数值一致性，再接六台真实 IMU 观测，最后安排受控真机测试。
记录中位/P95/P99/最大值、过期结果数、gap 次数和最终停止原因。
串口输出年龄与模型误差都不是机器人实际位置误差，报告时必须分开。

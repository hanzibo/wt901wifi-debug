# 迷你主机评估：仅 IMU 的真机演示

评估日期：2026-10-24。对象：商品图所示 i5-4590S、8 GB DDR3、128/256 GB SSD。

## 判断与限制

**精简演示值得测试，不能仅凭商品图保证双臂流畅。**
Ubuntu/Python 基本运行不是主要疑点；热点质量、图形驱动、IK 尾部耗时和散热更关键。
CPU 足够不等于整机可用；该型号主机的网卡、主板、SSD 和散热规格仍未知。
未在这款迷你主机上测试，不把本机测试结果称为目标主机验收。

Intel 官方：i5-4590S 为 2014 年产品，4 核 4 线程、基频 3.0 GHz、最高睿频 3.7 GHz、
65 W TDP，HD Graphics 4600，支持 AVX2 / 64 位。
它不是现代低功耗处理器；小机箱持续负载下须验证散热。
来源：[Intel 规格](https://www.intel.com/content/www/us/en/products/sku/80816/intel-core-i54590s-processor-6m-cache-up-to-3-70-ghz/specifications.html)。

可用 Ubuntu 24.04 LTS amd64 做兼容性测试。8 GB 可作为精简演示的候选，不建议同时开视觉、
仿真、浏览器和开发工具；这不是实测内存承诺。128 GB 能作为精简安装候选，256 GB 更利于环境和日志留存。
不要复制包含 CUDA/视觉模型的全部开发环境。
Ubuntu 安装指南要求至少 25 GB 磁盘空间，并提供安装前试用路径：
[官方安装指南](https://ubuntu.com/desktop/docs/en/24.04/tutorial/install-ubuntu-desktop/)。

## 当前代码实际做了什么

| 环节 | 代码证据 | 对资源的影响 |
| --- | --- | --- |
| UDP 收包 | `wt901/gui_udp.py:GuiUdpSource`；单 socket，非阻塞，一轮最多 512 数据报 | 多设备高频时有解析、排队、日志成本；当前在 GUI 线程轮询 |
| 姿态估计 | `pose.py:PoseEngine.feed`、`AdaptiveTiltFilter` | 每个在线设备都处理，包括未分配到部位的设备；陀螺积分、重力纠偏，不需 GPU |
| 人体映射 | 手动轴映射、自然下垂归零、`PoseEngine.transforms` | 可省穿戴标定，但不能省当前链路要求的设备在线与中立位/启动确认 |
| 人体显示 | `gui.py` / `body_view.py` | `run.py` 仍加载 15 部位 STL；20 ms 轮询，脏状态时渲染节流到不超过 30 FPS；**不是无渲染的最小程序** |
| 双臂 IK | `BilateralIK` 顺序求两侧 `SharedArmIK`，复用 `SceneSolver` | 数值最小二乘，两阶段任务；局部求解 `max_nfev=25`，不构成严格墙钟时间上限 |
| IK 线程 | `ArmIKWorker` | 仅保留最新待算输入，过期结果丢弃；不是无限队列；线程不保证 Python CPU 计算充分并行 |
| 串口规划 | `real_robot_transport.py`、Ruckig | 同一线程合成 54 字节帧、限速/限加速度、115200 8N1；发送与 IK 解耦 |
| 日志 | `Recorder` | 有界队列，异步 JSONL，逐行 flush；详细 acquisition 记录可能增长很快 |

仅跑 `OptUSBProj-ubuntu/run.py` 不会自动启动相机推理。不要用 `fusion_run.py` 启动本次基线。
不启动 RViz、CoppeliaSim、不勾选镜像，就不需要仿真进程或 NVIDIA GPU。
但人体窗口仍需 VTK/PyVista 与可用的 OpenGL；不能把“无相机”理解成“无图形开销”。
Mesa 的 llvmpipe 是 CPU 软件光栅化器，若实际使用它，显示可能抢占控制所需 CPU：
[Mesa 官方说明](https://docs.mesa3d.org/drivers/llvmpipe.html)。

20 Hz 时协议净荷约 1080 B/s；8N1 在线路上约占 10800 bit/s，约为 115200 的 9.4%。
单帧传输时间约 4.69 ms。这只说明线路带宽，不代表主控能按同速执行、更不代表物理动作无延迟。
本次不修改此前实测通过的频率、速度、加速度或断流保护。

## 既有日志提供的证据

本机实查 CPU 为 i7-14700HX（20 核、28 逻辑 CPU），系统可见总内存约 14 GiB。
2026-10-24 本次检查时系统已有约 10 GiB 使用、4 GiB swap 几乎占满。
这是开发桌面的瞬时状态，**不能归因于机器人进程**；不适合做受控跨机比较。

读取 `recordings/real_robot_imu/20261017-172237-887d0e/control.jsonl`：
该会话约 468 秒，从启动门控记录看是左臂模式，不能当双臂基准。

| 指标 | 样本数 | 均值 ms | P95 ms | P99 ms | 最大 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单次 IMU feed | 70253 | 0.612 | 1.223 | 1.570 | 13.830 |
| 主窗口一次 poll | 22977 | 4.489 | 8.696 | 12.272 | 27.431 |
| 左臂 IK | 5331 | 15.513 | 21.949 | 26.566 | 40.244 |
| 串口 write 调用 | 2193 | 1.475 | 6.530 | 10.082 | 13.950 |

这些是历史墙钟耗时，不是 CPU 使用率，也没有指定进程内存。
write 调用返回耗时不是电机响应时间，也未必是最后一位在线路上的完成时间。
该会话约 150 MB、含约 39.6 万条 acquisition 事件，部署机应考虑日志保留和磁盘余量。
全会话 write 间隔混有暂停和回位，不能把最大间隔直接认定为卡顿。

不能按 5.5 GHz / 3.7 GHz 换算；架构、每周期执行量、调度、内存、散热均不同。
也不能按“本机总 CPU 5%”直接推断旧机只用 5%。
100% 单核口径意味着占满一个逻辑 CPU；本机一个满载线程可只表现为整机约 3.6%。
[psutil CPU 统计口径](https://psutil.readthedocs.io/stable/index.html)。

## 已添加的只读记录器

### 推荐：直接通过真机窗口操作

重启程序，打开“真机受限 IMU 控制”窗口。顶部模式选择附近新增“运行性能记录”区域：

1. 选择“左臂仿真同源 IK”，加载已验证的参数，关闭相机和额外仿真/镜像。
2. 点击“开始性能记录（CPU / 内存 / 控制日志关联）”；无需 PID 或终端，可先于串口连接。
3. 按原安全流程连接串口、确认上电、锁定目标并开始随动，正常运行约 5–10 分钟。
4. 先按原流程安全停止机器人，再点击“停止性能记录并保存（不停止机器人）”。
5. 等待显示“性能记录已保存”，将界面显示的目录以及对应真机控制日志路径交回分析。

资源采样在独立子进程中每秒一次；不计入该采样进程自身的 CPU/内存。
正常 GUI/控制进程及其他子进程仍计入。最多记录 1 小时，到时只结束记录，不停止机器人。
记录器的故障不触发机器人控制操作；关闭控制窗口时，原有制动/断开流程优先，随后保存资源记录。
`samples.jsonl` 同时包含 `gui_context` / `gui_state` 事件：模式、参数、设备分配、
算法、控制日志路径及指令侧随动状态，方便区分准备、随动和暂停片段。
真机 `control.jsonl` 仍按原路径保存，资源目录通过上下文事件关联它，不复制大文件。
测试只记录，不自动改变模式或 checkpoint；没有新实现无 3D 的轻量控制入口。

`scripts/robot_runtime_probe.py` 不导入控制代码，不打开 UDP/串口，不自动选择进程，
不设置亲和性/频率/优先级，不启动或停止机器人。
它只记录指定 PID 与子进程：进程 CPU、最忙线程、RSS/PSS、系统可用内存、swap、系统频率。
系统 MHz 不是某控制线程的有效主频；RSS 相加可能重复计算共享页，PSS 不可读时记为缺失。
1 秒采样可能漏掉亚秒峰值，须与已有 IK / 收包 / 发送时序日志配合。

当前 `OptUSBProj-yolo` 已有 psutil 7.2.2，无需安装。
其他环境可按需安装 `requirements/runtime-probe.txt`。

### 建议分开记录三个 5–10 分钟工况

- A：相同在线 IMU 数，人体 GUI 显示，不连接串口。
- B：左臂或双臂按实际演示流程随动，带掌向，镜像/视觉关闭。
- C：仅在独立安全条件满足时，重复 B 并加入双手开合。

每次保存资源目录、真机 control.jsonl 路径、开始时间、在线设备数和发送频率。
先做低速小范围动作，再做正常演示。无需为跑分做极限动作或关闭保护。
数据记录器不提供物理急停；继续使用既有结束手势、暂停和独立断电措施。

## 如何判断能否迁移

### 如果只保留演示必需功能

建议增加独立的轻量启动入口，不删除原程序功能：

1. 不导入、不创建人体 STL / PyVista / VTK 预览；仅隐藏窗口不能消除这些开销。
2. 不启动相机、视觉模型、RViz、CoppeliaSim 或仿真镜像。
3. 只处理已选择的上臂、前臂、手背和必要指段设备。
4. 复用现有姿态估计、手动映射、双臂 IK 和唯一串口线程。
5. 只显示连接、输入新鲜度、控制状态和暂停按钮；状态显示约 2–5 Hz。
6. 正常演示只记状态变化、异常和周期性能摘要；详细逐包日志保留为调试选项。

这些删减主要省去显示、无关设备处理和磁盘写入，而不是取消安全约束。
IK 仍是关键计算成本；先测双臂耗时，再决定是否降低求解更新频率。
不要把降低界面刷新频率等同于降低 IMU 收包频率。

**我的工程判断：按这个精简目标，i5-4590S + 8 GB 有希望承担短时演示。**
这不是目标机实测结论，也不保证快速动作下的双臂更新速度。
无线热点和持续散热仍须实机验证。

以下是工程筛查目标，不是安全认证：

- 20 Hz 目标对应 50 ms 周期；优先看双臂 IK P95/P99 和连续更新时延，而非只看均值。
- 串口发送与 IK 独立，发送 20 Hz 不证明新的 IK 结果也是 20 Hz。
- 将本机 IK 耗时乘 2 / 3 / 4 只作敏感性分析，不当作旧 CPU 的真实性能比例。
- 希望目标机关键线程有明显余量，例如持续负载不贴近单核 100%；没有频繁的过期 IK / 输入 gap。
- 希望目标机总可用内存留至少约 1.5–2 GiB，稳定阶段没有持续 swap-in/out；按实测再修正。
- 热点必须让实际数量 IMU 连续运行，不能只验证一台能上网。
- 用目标机 Ubuntu Live USB 先看显示、网卡 AP 模式和 USB-TTL；完整安装后再测 20–30 分钟持续演示。

网络适配器支持 Wi-Fi 不等于支持所需 AP 模式/设备数。
购买前让商家提供芯片型号及 Linux AP 支持信息。
NetworkManager 明确按设备能力建立热点：
[官方热点文档](https://networkmanager.dev/docs/api/latest/nmcli.html)。
若内置无线不可靠，可让迷你主机有线连接独立 AP/路由器，IMU 连接该 AP；
须按原设备地址/端口重新核对数据通路，这与提高 CPU 配置不是一回事。

如果本机数据表明 IK 或渲染占用过高，下一步再加“无人体 3D 预览”的专用入口，
复用现有姿态、IK、安全状态机和单串口线程。**本轮未改动控制路径，也未实现该无渲染入口。**
不要为了降低演示成本而取消断流保护、限速或人工上电确认。

# 真机接入准备：OptUSBProj 原始通信代码审查

日期：2026-10-13。分支：`codex/real-robot-integration`。

## 范围与结论

本轮仅静态阅读与离线编码验证。没有打开串口、连接机器人或发送控制命令。
`OptUSBProj/` 仍是被忽略的原始代码目录，不修改、不纳入 Git。
IMU、RGB-D、穿戴标定、人体模型和现有仿真入口均未修改。

可以复用现有姿态估计与机器人 IK 的目标生成链路，但真机必须新增独立后端。
发现的主链路是双臂六自由度、双手各五个控制量的 54 字节二进制串口协议。
这不是 AmazingHand 八舵机协议，也不是 X1 RViz `/joint_states` 协议。
它与当前 CoppeliaSim 场景的对象命名一致，但不能仅凭名称证明电机零点与方向一致。
协议结论来自 PC 发送代码；没有下位机源码或固件协议说明来确认接收语义。

## 主链路数据流

原始 IMU 链路：

`IMU → DH 关节角 → angleCastDH2Sim → 仿真关节角 → anglesCastSim2Real → 二进制帧 → 串口`

当前拟接入链路：

`已标定人体姿态 → SceneArm IK → 命名关节目标 → 真机映射配置 → 安全门控 → 编码 → 独立串口线程`

CoppeliaSim 求解器输出的是场景实际关节坐标，不是 DH 角。
若确认场景与原硬件同轴同零点，就不应再调用 DH→Sim，否则会重复变号和偏置。
最终映射需配置为每轴符号、零点、允许范围，而不是在多个 UI 中重复加 90°。

## 从端发送帧：零起始字节偏移

| 偏移 | 长度 | 内容 |
|---|---:|---|
| 0–1 | 2 | `AA 55` |
| 2–13 | 12 | 右臂 J1–J6，各两字节 |
| 14–25 | 12 | 左臂 J1–J6，各两字节 |
| 26–31 | 6 | 测试 UI 中 H1、H2、Waist；IMU 与转发代码固定为三个 9000 |
| 32–39 | 8 | 右手五个 12 位控制量，共 60 位；末尾四位填零 |
| 40–47 | 8 | 左手五个 12 位控制量，同上 |
| 48–51 | 4 | 固定零；语义未提供 |
| 52–53 | 2 | 前 52 字节的无符号字节总和，小端；不是 CRC |

关节编码为 `int16` NumPy 本机字节序。
在当前 x86 Linux 上为小端，未来实现应显式使用小端，不依赖主机字节序。
物理单位按发送代码推定为 0.01°：`u = trunc(100 × (degrees(q_sim) + 90))`。
手指范围由测试 UI 限制为 0–4095，0 为展开、4095 为闭合的意图可从键盘控制看出。
五指顺序在碰撞模型中为拇指、食指、中指、无名指、小指；仍需硬件逐指确认。

重要：完整帧会写所有通道。仅操作一侧也必须为其他侧、头部和腰部给出已确认的保持目标。
不能用默认 90° 代替“保持当前位置”。

## 不同角度空间与中立位

原始 Sim→DH：

```
R: [-q1, -q2, q3, q4+π/2, -q5-π/2, q6]
L: [-q1,  q2, q3, q4+π/2, -q5+π/2, -q6]
```

原始串口映射：两侧各轴均为 `degrees(q_sim)+90°`。
当前 `SceneArm.neutral` 为 `[0,0,0,-π/2,0,0]`。
若直接使用原串口公式，中立位会编码为 `[90,90,90,0,90,90]°`，每侧相同。
这说明场景中立位不是“所有电机 90°”，不能在连接时自动归零。

原始测试窗口的电机角范围（度）：

| 侧 | J1 | J2 | J3 | J4 | J5 | J6 |
|---|---|---|---|---|---|---|
| 右 | 0–235 | 90–240 | 0–180 | 0–118 | 0–180 | 50–121 |
| 左 | 0–226 | 90–234 | 0–180 | 0–119 | 0–180 | 51–122 |

以上是旧 PC 代码中的历史参数，不是已经验证的当前硬件安全范围。
腕部 J6 特别窄，不能沿用仿真宽限位或此前为演示提高的腕部速度。
DH 模型中的 J6 还有与窗口范围不一致的宽限位，需统一真机配置来源。

## 原始实现的风险与不足

1. **没有执行反馈协议。** 串口只读取任意字节并打印，没有帧解析、ACK、位置或故障状态。
   写成功仅表示交给操作系统，不代表电机接收或到位。
2. **限位不一致。** 手动窗口与主手转发路径有裁剪；IMU `sendCtrlCmd` 和编码器未统一校验范围。
3. **有符号溢出。** 手动 UI 允许 360°，36000 转 `int16` 会变成 -29536。
   当前旧臂限位上限较低，但头部／腰部或错误输入仍可能触发。
4. **没有独立新鲜度／使能／失联保护。** 不能把仿真短暂断流自动恢复策略直接搬到真机。
5. **线程归属问题。** `QThread` 对象创建于 GUI 线程，`_sendCmd` 未移入 worker。
   信号调用并不保证写串口发生在串口工作线程；写操作还没有显式 `write_timeout`。
6. **FIFO 积压。** 主手转发每 20 ms 取一个命令，无界 `Queue` 可能让旧目标延迟执行。
7. **路径速度未统一。** IMU UI 20 ms 发送、每五次触发新求解，五点线性插值约 100 ms。
   这是平滑策略，不是经过硬件验证的最大速度／加速度限值。
8. **碰撞行为不等于安全控制器。** 手动测试检测后仍发送；IMU UI 的阻止发送取决于开关。
   原包围体检测也不能证明覆盖所有危险构型。
9. **停止发送不等于急停。** 现有代码关闭串口，没有可确认的电机断能／制动命令。
10. **没有下位机 watchdog 证据。** PC 卡死后是否保持、继续运动或停止，当前无法确认。

TCP 主手输入另有长度、命令等字段，解析器未校验校验和与最小命令长度。
`GenCmdTest` 的主手帧和 JSON 示例只可作辅助参考，不能混进从端协议。

## 仿真手型如何转给真机

当前仿真允许每手 15 个独立关节角，但真机帧只提供每手五个量。
原 `CoppSimEnv` 用一个手指控制量等比例驱动该指三个关节。
因此十五维任意手型一般无法精确转换成这五个量。
建议第一版直接复用已经稳定的开／闭状态，配置每手五个展开值与五个闭合值。
十五关节端点继续用于仿真，五通道端点单独用于真机，不偷偷相互覆盖。
之后若需要连续手型，再标定各指的单输入耦合曲线。

## 建议模块与分阶段接入

- `robot_protocol`：纯编码／解码，不导入 Qt、serial、相机；显式大小端和范围校验。
- `robot_profile`：命名关节顺序、符号、零位、硬限位、速度／加速度及手指端点。
- `robot_transport`：单线程独占串口，最新值邮箱、有界日志、收发统计和超时。
- `robot_safety`：独立使能、新鲜度、幅度／速率校验、故障锁止、人工重新使能。
- `real_robot_gui`：默认干运行；区分连接、使能、写成功、收到反馈、到位状态。

阶段一：纯编码与离线／伪串口测试，展示待发送帧，不控制硬件。
阶段二：确认固件、串口和安全条件，再读取真实反馈；打开串口本身也可能改变 DTR/RTS。
阶段三：有人值守、物理急停可用时，逐轴小幅点动核对方向和零点。
阶段四：单臂低速随动，然后双臂；手指与头腰最后独立验收。
真机模式必须单独启用，不能因仿真窗口已跟随而自动发送。

## 本轮离线验证

审查脚本 `/tmp/wt901_original_protocol_audit.py` 仅通过 AST 提取三个编码函数。
不导入原始模块，不执行原始 GUI 或任何串口／网络代码。
1000 组随机输入：两处生产编码器与独立 `struct`／位打包结果完全一致。
手动编码器的手指打包也通过比较；检查帧长、顺序、校验和。
这证明编码逻辑一致，不证明真实固件接受或动作安全。

115200、8N1 假设下，54 字节纯线缆时间为 4.6875 ms。
50 Hz 时每秒 2700 字节，约占理论串口字节吞吐的 23.4%。
不包括 USB、调度、反馈与固件处理延迟，不能据此承诺实时性。

## 真机接入前需确认

- 接入的具体机器人是否就是 `NowRobotWithHand1` 对应硬件？
- USB 串口是否直接连该控制板，是否存在无线桥接，固件版本是什么？
- 下位机接受 54 字节帧，还是另一个含长度字段的协议？
- 各轴电机零点、正方向、可用角范围及速度／加速度参数。
- 未控制侧、头部、腰部当前角度与如何可靠保持。
- 是否支持位置／故障反馈、扭矩使能、物理急停与失联 watchdog。

在这些问题确认前，可以继续做干运行和伪串口链路，但不能默认全身实发。
